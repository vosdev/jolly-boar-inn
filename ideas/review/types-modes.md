# Question types and modes review

Read CLAUDE.md, all of ideas/architecture.md, phase2.md T16–T32, games.md, every `questions/` and `modes/` module, `random_events.py`, the type- and mode-dependent parts of `rooms/state.py`, `selection.py`, `settings.py`, `segments.py`, `scoring.py`, `ws/protocol.py`, `http/modes.py`, every client question component, `lib/modes.ts`, `protocol.ts`, `Room.svelte`, `RandomEvent.svelte`, `RevealTally`, `PointsSlot` and the pack files. No tests, servers or browsers were run. Ordering and pick-all-that-apply do not exist yet, so the findings about them are about design, not observed bugs.

`custom` and `random_event` have no type and no round. Their questions each carry a type and all play for 20 s (range 10–60), whatever that type is.

**What the engine does well.** `state.py` stays type-blind: it calls `client_view`, `validate_value`, `grade`, `reveal` and `scoring_of` through `TYPES[question.type]`. `protocol.py` carries `value: Any`, `view: dict` and `reveal: dict`. `answers.value` is jsonb. `PlayerResult.credit` already exists. An array-valued answer for ordering or pick-all needs no change to the protocol, the SQL or `submit_answer`.

### Cost of one new mode on an existing type (for example Bestiary on `multiple_choice` with `TextStem`)

Files you have to touch: `modes/__init__.py` (one line), a generator script, a Makefile target until T24, the generated pack, the generator's test, `tests/test_modes.py`, and the `MODES` entry in `lib/modes.ts`. Optionally a splash mark in `assets/scenes/marks/`. The version bump adds four more: `VERSION`, `pyproject.toml`, `package.json` and `uv.lock`. A new stem adds three: `stems/X.svelte`, the `StemId` union and the `STEMS` map. That is about 7 source files, and none of them is the engine, the protocol, the schema, selection, settings, `Question.svelte` or `Room.svelte`.

Three of those touches should not be needed (see TM-10 to TM-12):
- the exact-registry snapshot in `test_modes.py`;
- `type` in `lib/modes.ts`, which nothing on the client reads;
- `vocab` in `lib/modes.ts`, which repeats the pack payload.

## High

### TM-1. A mode can have only one type, and "no type" also means "not a round"
- **Where:** [server/app/modes/mode.py:33](../../server/app/modes/mode.py#L33), [mode.py:37-40](../../server/app/modes/mode.py#L37), [server/app/questions/schema.py:110](../../server/app/questions/schema.py#L110), [server/app/rooms/settings.py:168](../../server/app/rooms/settings.py#L168), [server/app/rooms/selection.py:181](../../server/app/rooms/selection.py#L181), [server/app/modes/__init__.py:66-86](../../server/app/modes/__init__.py#L66), [server/app/http/modes.py:32-33](../../server/app/http/modes.py#L32), [client/src/lib/modes.ts:36](../../client/src/lib/modes.ts#L36)
- **Problem:** `Mode.type` is one `str | None`, and `is_round` is defined as `type is not None`. `mode_errors` rejects every pack question whose type is not exactly the mode's. Pace falls back through that single type, and selection's "prefer a different type" compares against it. games.md (4deab42) now plans modes that mix `multiple_choice` with a pick-all type. The only way the registry can express "several types" today is `type=None`. That silently turns the mode into a non-round: `settings.py:168` refuses it, `/api/modes` sends `questions: null`, and Create hides it.
- **Why it matters:** This blocks the planned pick-all questions inside Bestiary, Drop Table, Odd One Out and Who Said That? (T25–T29), and the obvious workaround breaks the mode without an error. It was a deliberate decision (architecture §1: "Every other mode has a type, and validate_packs.py rejects…"), but games.md's newer plan contradicts it.
- **Fix:** Decide before T25. There are two ways. (a) Keep one type per mode and make pick-all a variant of `multiple_choice`: `answer_indices` as an alternative to `answer_index`, with `grade`, `validate_value`, `reveal` and the view branching on it. The registry and the engine stay as they are. (b) Use `Mode.types: tuple[str, ...]` plus an explicit `round: bool`. `mode_errors` then checks membership, a mode with several types must state its own `Bounds`, and selection compares against the set. Either way, update architecture §1/§2 in the same PR.

## Medium

### TM-2. An event question's stem is picked by mode, so a `price_is_right` event has no item
- **Where:** [client/src/lib/modes.ts:134](../../client/src/lib/modes.ts#L134), [modes.ts:146](../../client/src/lib/modes.ts#L146), [client/src/components/questions/index.ts:56-61](../../client/src/components/questions/index.ts#L56), [stems/TextStem.svelte:19](../../client/src/components/questions/stems/TextStem.svelte#L19), [types/PriceIsRight.svelte:47](../../client/src/components/questions/types/PriceIsRight.svelte#L47), [PriceIsRight.svelte:67](../../client/src/components/questions/types/PriceIsRight.svelte#L67), [schema/question.schema.json:81-92](../../schema/question.schema.json#L81)
- **Problem:** `viewFor(type, mode)` takes the stem from the mode alone. `custom` and `random_event` both name `text`, and `TextStem` only reads `prompt`. A `price_is_right` payload has no `prompt`, so a host's or an NPC's price question shows four prices under "What does it go for on the Grand Exchange?" and never names the item. A `more_less` event draws nothing while it is held, because its view *is* the question. `price_is_right` also has no `metric`, although architecture §2 says a hand-written price question should use `high_alch` or `shop_price`. The client always says "Grand Exchange".
- **Why it matters:** The schema, `custom.envelopes` and the NPC packs all accept these questions, and the docs invite them. Players then get a question they cannot answer.
- **Fix:** When the mode has no type, fall back to a stem per type in `index.ts` (`price_is_right → asset`, `more_less → none`, anything else → `text`). Add `metric` to `price_is_right` and drive both the question line and the reveal from it, the way `MoreLess` already does. Or have `mode_errors` refuse these two types in `custom`/`random_event` until they get one.

### TM-3. The type contract has no step that normalises an answer, and nothing guards credit
- **Where:** [server/app/questions/types/__init__.py:3-7](../../server/app/questions/types/__init__.py#L3), [server/app/rooms/state.py:1221](../../server/app/rooms/state.py#L1221), [state.py:1231-1239](../../server/app/rooms/state.py#L1231), [state.py:1574-1584](../../server/app/rooms/state.py#L1574), [server/app/rooms/scoring.py:106](../../server/app/rooms/scoring.py#L106), [state.py:1393](../../server/app/rooms/state.py#L1393)
- **Problem:** `validate_value` returns a bool. Whatever the client sent is stored, echoed back in `results` and `welcome.your_answer`, and passed to `grade` unchanged. Pick-all answers such as `[2,0]`, `[0,2]` and `[0,0,2]`, and ordering permutations, will each need their own order and duplicate handling in both `validate_value` and `grade`, and again in the client view. Credit is also unguarded. `points_for` raises on credit outside 0..1 inside `_close_question`, and the timer task catches that, logs it and stops, which leaves the room stuck. Pick-all's natural "right minus wrong" credit goes negative. Credit built by summing fractions misses 1.0: `sum([0.1] * 10)` is 0.9999999999999999, so `correct` comes out false.
- **Why it matters:** Both planned types are the first with multi-value answers and partial credit, which are exactly where these gaps bite. A grading bug turns into a hung room instead of a zero.
- **Fix:** Replace `validate_value` with `parse_value(payload, value) -> canonical | None` (sorted, deduplicated, trimmed), and store and grade the canonical value. Pass `grade`'s output through one engine helper that rounds to about 1e-9 and clamps to 0..1, logging the type's bug rather than raising. Give each type a property test: every value `parse_value` accepts must grade into 0..1.

### TM-4. `GemChoices` only handles one answer and submits on tap
- **Where:** [client/src/components/questions/GemChoices.svelte:31-34](../../client/src/components/questions/GemChoices.svelte#L31), [GemChoices.svelte:61-62](../../client/src/components/questions/GemChoices.svelte#L61), [GemButton.svelte:33-42](../../client/src/components/questions/GemButton.svelte#L33)
- **Problem:** `picked` and `answer` are `number | null`. The first tap sends the answer and locks every button. `gemState` has five states, all assuming a single right answer, and the reveal layout makes the one answer `large`. Pick-all needs toggling, a Submit button, and reveal states for "right and picked", "right and missed" and "wrong and picked". `GemButton`'s docstring also names `ordering` as a future user, but nothing here can reorder.
- **Why it matters:** `MultipleChoice` and `PriceIsRight` share this component. Pick-all has to either fork it or refactor it under both of them, and the extra states are something players see, so design has to decide them (CLAUDE.md).
- **Fix:** Generalise it to `picked: ReadonlySet<number>`, `answer: ReadonlySet<number>` and `select: 'one' | 'many'`, and add a `missed` state. Get the look agreed as a D-task before pick-all lands.

### TM-5. Nothing decides the order ordering entries are shown in
- **Where:** [server/app/rooms/state.py:340](../../server/app/rooms/state.py#L340), [ideas/phase2.md:423-437](../phase2.md#L423), [ideas/architecture.md:575-582](../architecture.md#L575)
- **Problem:** `client_view(payload)` gets only the payload, and it runs again on every open and every `welcome`. The ordering spec stores `entries` with `rank` plus the answer order, but never says in what order `client_view` shows the entries. NPC and host questions are hand-written, and a writer naturally lists entries in rank order. A pass-through `client_view` then shows the answer.
- **Why it matters:** The answer leaks on the wire and on screen for every hand-written ordering question. The shuffle has to be deterministic, because every socket and every reconnect must see the same order (architecture §3, "byte-identical").
- **Fix:** Add to T27: `client_view` drops `rank`/`detail` and orders `entries` by a shuffle seeded from the content hash of the payload, and never in `answer` order. An accept criterion should check that a payload written in answer order is not shown in answer order.

### TM-6. The client views copy the same scaffolding six times
- **Where:** [types/FreeText.svelte:39-62](../../client/src/components/questions/types/FreeText.svelte#L39), [types/ClosestNumber.svelte:45-78](../../client/src/components/questions/types/ClosestNumber.svelte#L45), [types/PickFromList.svelte:87-88](../../client/src/components/questions/types/PickFromList.svelte#L87), [PickFromList.svelte:190-200](../../client/src/components/questions/types/PickFromList.svelte#L190), [types/MultipleChoice.svelte:56-62](../../client/src/components/questions/types/MultipleChoice.svelte#L56)
- **Problem:** All six views repeat the "not scored for you" note word for word. The three text-entry views each rebuild `answered`/`locked`, the "It was X / Your answer: Y" card, the 56px input and Submit row, and the same `.row`, `.settled`, `.picked` and `.explanation` CSS. Three views render `explanation` themselves. `PickFromList` drops it even though `pick_from_list.reveal` sends it ([pick_from_list.py:57](../../server/app/questions/types/pick_from_list.py#L57)).
- **Why it matters:** Ordering and pick-all will make it eight copies, and every D-task restyle of question screens has to touch each one. The `explanation` gap shows that the copies already drift.
- **Fix:** Draw the "not scored" note and the revealed `explanation` once, in `Question.svelte`, which already has `you_can_answer` and `data`. Extract `AnswerForm` (input row plus Submit) and `AnswerSettled` (the answer line plus your line) for the text-entry views.
